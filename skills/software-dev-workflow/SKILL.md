# 软件开发标准流程

当用户要开发软件时，按此流程引导，不要跳步。每一步完成后与用户确认再进入下一步。

## Procedure（流程步骤）

1. **需求澄清**：让用户用自己的话描述要做什么。追问：目标用户是谁？解决什么问题？核心场景是什么？不做什么（边界）？
2. **需求结构化**：把需求整理为结构化文档——背景/目标/用户故事/功能清单（分 P0 必须、P1 重要、P2 可选）/非功能需求（性能、隐私等）/边界与约束。输出给用户确认。
3. **产品方案**：基于确认的需求产出方案——信息架构、核心流程、页面/模块划分、关键交互。输出 PRD 级别的文档。
4. **技术方案**：选型（语言/框架/存储/部署）、模块设计、数据模型、接口定义、风险点。给出里程碑拆分。
5. **研发实施**：按里程碑开发。每个里程碑保持可运行状态，完成后自测再进入下一个。
6. **测试**：功能测试（对照功能清单逐条验收）、边界情况、回归测试。输出测试报告。
7. **上线**：部署清单（环境变量、依赖、数据迁移）、灰度/回滚预案、上线后观察指标。

## Specifications（完成标准）

- 每个阶段有明确的产出物（需求文档/PRD/技术方案/代码/测试报告/上线清单）
- 需求文档经用户书面确认后才进入方案阶段
- 上线前测试报告必须覆盖全部 P0 功能

## Advice（经验提醒）

- 用户往往只想清楚了三成需求，需求澄清阶段多问比多问少强
- 功能清单砍到 P0 能跑通再谈 P1——上线一个小的完整版本胜过大的半成品
- 技术选型优先用用户已熟悉的栈，除非有明确理由

## Forbidden Actions（禁止事项）

- 不要在需求未确认时直接开始写代码
- 不要跳过测试直接给出"可以上线了"的结论
- 不要替用户做他不了解的技术决策而不解释取舍

## Required from User（需要用户提供）

- 需求描述与目标用户
- 每个阶段产出物的确认
- 可用的开发资源与时间约束
